## 0. ข้อค้นพบก่อนเริ่ม — อ่านก่อนประเมินงาน

เอกสารนี้เขียนจากการอ่านโค้ดจริง ไม่ใช่จากการคาดเดา และการอ่านนั้นเปลี่ยนรูปของงานไปพอสมควร

### 0.1 SSOT ที่ขอ มีอยู่แล้วครึ่งหนึ่ง

Daily Note **ไม่ใช่** ตารางแยก — มันคือ `Note` ธรรมดาที่ `type = 'list'`, `tags` มี `daily`
และ `scheduledFor` ชี้วันนั้น ส่วน To-do ทั้งหมดอยู่ในคอลัมน์ `checklistItems` (JSON) ของโน้ตใบเดียวกัน

แปลว่า **FR-1 (sync ไปเป็นโน้ตชื่อ "Daily Note - [Date]") ทำงานอยู่แล้ว** — `dailyNoteTitle()`
ตั้งชื่อโน้ตให้ และโน้ตนั้นโผล่ในปฏิทินอยู่แล้วเพราะมี `scheduledFor`
สิ่งที่ยังขาดคือ **การบอกผู้ใช้ว่ามันเกิดขึ้น** ไม่ใช่ตัวกลไก sync

### 0.2 ระบบยังไม่มี "ปฏิทินนัดหมาย" เลยแม้แต่ตารางเดียว

ในสคีมามี model ชื่อ `Event` จริง แต่ **ไม่ใช่** event ปฏิทิน — มันคือ error event ของ Bug Tracker
(มี `projectId`, `issueId`, `level`, `stack`) ผูกกับ Project และ Issue

> ⚠️ หัวข้อ **Agenda (events)** ใน FR-4 **ไม่มีที่เก็บข้อมูลรองรับเลย** ต้องสร้าง entity ใหม่
> **ห้าม reuse ตาราง `Event` และห้ามตั้งชื่อซ้ำ**

### 0.3 To-do Master List สร้างไม่ได้บนโครงปัจจุบัน

เมื่อ To-do เป็น JSON ในโน้ตรายวัน คำถามว่า "งานค้างทั้งหมดของฉันมีอะไรบ้าง" ต้องดึงโน้ตทุกใบ
มาไล่อ่าน JSON ในหน่วยความจำ — index ไม่ช่วย, กรองตามวันครบกำหนดไม่ได้, และงานหนึ่งชิ้นข้ามวันไม่ได้
**นี่คือเหตุผลเชิงเทคนิคเพียงข้อเดียวที่บังคับให้ต้องเปลี่ยนสคีมา** (ดู D1)

## 1. สถานะปัจจุบัน เทียบกับข้อกำหนด

ตารางนี้ป้องกันทีมสร้างของที่มีอยู่แล้วซ้ำ **ให้ประเมินงานจากคอลัมน์สถานะ ไม่ใช่จากจำนวนข้อกำหนด**

| ข้อกำหนด | สถานะ | ของจริงในระบบวันนี้ | สิ่งที่ต้องทำ |
|---|---|---|---|
| FR-1 · โน้ตไปโผล่เป็น "Daily Note - [Date]" | ✅ **เสร็จ** | `dailyNoteTitle()` ให้ `Daily Note - 16 Aug 2026` ตรงสเปกแล้ว (2026-08-17) | — |
| FR-1 · แบนเนอร์/แบดจ์แจ้งผู้ใช้ | ✅ **เสร็จ** | `DailyNoteBadge` เปลี่ยน tense ตามสถานะจริง และลิงก์ `/notes?note=<id>` เปิดโน้ตใบนั้นตรง ๆ | — |
| FR-2 · เลย์เอาต์ซ้าย/ขวา 60/40 | ✅ **เสร็จ** | grid `1.6fr / 1fr` ≈ 61.5 / 38.5 ผ่าน container query | — |
| FR-2 · Mini Calendar คอลัมน์ขวา | ✅ **เสร็จ** | `MiniMonth` + `DayAgendaStrip` · คลิกเปลี่ยนวันโดยไม่ reload | — |
| FR-2 · To-do + ฟิลเตอร์ All/To do/Done | ✅ **เสร็จ** | `SegmentedControl` + กลุ่ม To do / Done อ่านจาก `tasks` แล้ว | — |
| FR-3 · To-do เข้าปฏิทิน | ✅ **เสร็จ** | month endpoint คืน `tasksByDay` + `eventsByDay` · marker บนกริดแยกชนิดได้ | — |
| FR-3 · To-do Master List | ✅ **เสร็จ** | `/tasks` กรอง open/done/overdue + ค้นหา จัดกลุ่มตามวัน ใช้ index · `RescheduleControl` เลื่อนงานไปวันอื่นได้จากรายการ | — |
| EC-11 · งานค้างข้ามวัน | ⚠️ **เปลี่ยนรูปแบบ 2026-08-19** | เดิม `CarriedOverBand` บน `/daily` — ถอดไปพร้อมหน้านั้น (§8 เฟส 3.5) ตอนนี้ใช้ฟิลเตอร์ **Overdue** บน `/tasks` แทน ยังไม่มีแถบเฉพาะ | ถ้าต้องการแถบกลับมาบน `/tasks` |
| FR-4 · Side panel: Agenda | ✅ **เสร็จ** | `CalendarEvent` + `EventDialog` สร้าง/แก้/ลบได้จาก panel | — |
| FR-4 · Side panel: Tasks | ✅ **เสร็จ** | ติ๊กงานจาก panel เขียนถึง server จริง | — |
| FR-4 · Side panel: ลิงก์โน้ตรายวัน | ✅ **เสร็จ** | `DayDetailPanel` สามส่วนครบ + ปุ่มไป `/daily?date=` | — |

## 2. การตัดสินใจเชิงสถาปัตยกรรม

### D1 — ยก To-do ขึ้นเป็นตาราง `Task` ของตัวเอง

To-do ย้ายออกจาก `Note.checklistItems` ไปเป็นแถวจริง มี `scheduledFor`/`dueDate` ของตัวเอง
และมี FK ชี้กลับโน้ตรายวันแบบ optional

**เหตุผล:** Master List, กรองตามวันครบกำหนด, เลื่อนงานข้ามวัน, แสดง Task รายชิ้นในปฏิทิน —
ทั้งสี่อย่างคือ query ที่ JSON ตอบไม่ได้

**ข้อควรรู้:** คอมเมนต์ในโค้ดเดิมเลือก JSON อย่างจงใจ เพราะ *"ตารางที่สองแปลว่ามีสองคำตอบว่าวันอังคารมีอะไร"*
เหตุผลนั้น **ถูกต้องสำหรับขอบเขตเดิม** และหมดอายุเพราะโจทย์เปลี่ยน ไม่ใช่เพราะเดิมคิดผิด
กัน "สองคำตอบ" ด้วย D3 แทน

### D2 — สร้าง `CalendarEvent` เป็น entity ใหม่ ไม่ยัดลง Note

นัดหมายมีช่วงเวลาเริ่ม–จบ, all-day flag และสถานที่ ซึ่งโน้ตไม่มีและไม่ควรมี
ถ้าใช้ Note แทน ต้องเพิ่ม `startAt`/`endAt`/`isAllDay` ที่เป็น null สำหรับโน้ต 95% ของระบบ

### D3 — "วัน" มีเจ้าของข้อมูลชัดเจนหนึ่งเดียวต่อชนิด

SSOT ไม่ได้แปลว่าทุกอย่างอยู่ตารางเดียว แต่แปลว่า **ข้อมูลแต่ละชนิดมีที่อยู่เดียว**

- ข้อความบรรยาย → `Note` เท่านั้น
- งานที่ต้องทำ → `Task` เท่านั้น
- นัดหมายมีเวลา → `CalendarEvent` เท่านั้น
- **ตัวเชื่อมคือฟิลด์ `scheduledFor` (วันที่)** ไม่ใช่การคัดลอกข้อมูลหากัน

**ผลที่ตามมา:** ไม่มีการ "sync" ในความหมายของการคัดลอก ทุกหน้าจอเป็นเพียง view ที่ query วันเดียวกัน
จึงไม่มีทางไม่ตรงกัน

### D4 — timezone ใช้ `User.timezone` เป็นแหล่งเดียว

ปัจจุบัน `/daily` คิด "วันนี้" จากนาฬิกาเบราว์เซอร์ (`dayjs()`) แต่ API ปฏิทินคิดจาก `User.timezone`
(ค่าเริ่มต้น `Asia/Bangkok (GMT+7)`) — ไม่ตรงกันเมื่อผู้ใช้เดินทาง

- ทุกการแปลง "เวลา → วัน" ต้องผ่าน helper ตัวเดียวที่อ่าน `User.timezone`
- คงไว้: `scheduledFor` เขียนเป็น **เที่ยงวันท้องถิ่น** ไม่ใช่เที่ยงคืน เพราะเที่ยงคืนห่างจากวันข้างเคียง
  แค่ค่า offset เดียว แล้ววันจะเพี้ยนหลัง round-trip ผ่าน UTC

### D5 — การลบเป็น soft-delete สำหรับ Task และ Event

ใช้ `deletedAt` แทนการลบจริง เพราะการลบโน้ตรายวันหนึ่งใบไม่ควรทำให้ประวัติงานที่ทำเสร็จแล้ว
หายไปจากปฏิทินย้อนหลัง (ดู EC-01)

## 3. User Stories & Acceptance Criteria

ทุก AC เขียนให้ **ทดสอบได้** — มีตัวเลข มีสถานะเริ่มต้น และมีผลลัพธ์ที่สังเกตเห็นได้
ข้อไหนพิสูจน์ไม่ได้ว่าผ่าน ถือว่ายังไม่เสร็จ

### US-01 — เขียนโน้ตรายวันแล้วรู้ว่ามันไปอยู่ไหน

- หน้า `/daily` แสดง badge ว่า **"บันทึกนี้จะกลายเป็นโน้ตชื่อ *Daily Note - [วันที่]* ใน Notes & Calendar"**
- badge กดได้ และนำไปยังโน้ตใบนั้นโดยตรง (ไม่ใช่หน้ารวม)
- ก่อนพิมพ์ตัวอักษรแรก ใช้ถ้อยคำอนาคต ("จะกลายเป็น"); หลังบันทึกแล้วเปลี่ยนเป็นปัจจุบัน ("ถูกบันทึกเป็น")
- เปิด `/notes` ต้องพบโน้ตชื่อเดียวกันบนวันเดียวกันในปฏิทิน

### US-02 — เห็นโน้ตและงานของวันพร้อมกันในจอเดียว

- ที่ความกว้าง container ≥ 56rem แสดงสองคอลัมน์ อัตราส่วน ≈ **60 : 40**
- ต่ำกว่านั้นเรียงคอลัมน์เดียว โดยโน้ตอยู่บน
- ไม่เกิด horizontal scroll ที่ 375 / 768 / 1280 / 1440 px
- **breakpoint วัดจากความกว้าง container ไม่ใช่ viewport** (เหตุผลใน §5)
- เปิด/ปิด AI panel แล้วเลย์เอาต์ปรับตัวถูกต้องโดยไม่ต้องรีเฟรช

### US-03 — บันทึกอัตโนมัติและรู้สถานะเสมอ

- ไม่มีปุ่ม Save — บันทึกเองภายใน 1.5 วินาทีหลังหยุดพิมพ์
- ตัวบ่งชี้ครบ 5 สถานะ: `ยังไม่มีอะไรให้บันทึก` · `มีการแก้ไข` · `กำลังบันทึก` · `บันทึกแล้ว HH:mm` · `บันทึกไม่สำเร็จ + ปุ่มลองใหม่`
- สถานะ "ไม่มีอะไรให้บันทึก" ต้องไม่แสดงเป็นช่องว่าง — ความเงียบถูกอ่านว่าระบบพัง
- `Ctrl/Cmd + S` บังคับบันทึกทันที และห้ามให้ dialog "save page" ของเบราว์เซอร์เด้ง
- ระหว่างบันทึก **ห้ามปิดการแก้ไข editor** (ตำแหน่งเคอร์เซอร์จะหาย)

### US-04 — เห็นบันทึกที่เขียนไว้แล้วเป็นการ์ด ไม่ใช่ช่องพิมพ์เปล่า

- วันที่มีเนื้อหาแล้ว เปิดมาเห็น **การ์ดบันทึก** พร้อมปุ่มแก้ไข
- วันที่ยังว่าง เปิดมาเข้าโหมดพิมพ์ทันที (ไม่ต้องกดปุ่มก่อน)
- การ์ด render รูปแบบเดิมครบ (ตัวหนา สี หัวข้อ ลิสต์)
- การ์ดแสดงจำนวนคำ และเวลาบันทึกล่าสุด
- **ตัดสินโหมดจากข้อมูลที่บันทึกแล้ว ไม่ใช่ state ใน editor** (ดู EC-08)

### US-05 — เพิ่มงานแล้วเห็นทันทีทั้งสามที่

- สร้าง To-do ที่ `/daily` แล้วปรากฏใน (1) รายการของวัน (2) ปฏิทินวันนั้น (3) Master List **โดยไม่ต้องรีเฟรช**
- งานใหม่บันทึก `scheduledFor` = วันที่กำลังเปิดอยู่ **ไม่ใช่วันนี้เสมอ**
- ติ๊กเสร็จ บันทึก `completedAt` เป็นเวลาจริง แสดงรูปแบบ `HH:mm`
- ยกเลิกติ๊ก **ต้องล้าง `completedAt` เป็น null** ไม่ใช่คงค่าเดิม
- ปฏิทินแยกให้เห็นว่า "มีงาน 3 ชิ้น เสร็จ 1" ไม่ใช่แค่จุดเดียว

### US-06 — ดูงานค้างทั้งหมดข้ามวันได้ที่เดียว

- Master List กรองได้: ค้าง / เสร็จแล้ว / เลยกำหนด / ช่วงวันที่
- งานที่ `dueDate` ผ่านมาแล้วและยังไม่เสร็จ มีสถานะ **เลยกำหนด** ที่เห็นได้โดยไม่ต้องอ่านวันที่
- เลื่อนงานไปวันอื่นได้จากรายการนี้ และปฏิทินอัปเดตตาม
- **query ต้องใช้ index** — ห้ามดึงโน้ตทุกใบมากรองใน memory

### US-07 — คลิกวันในปฏิทินแล้วเห็นทุกอย่างของวันนั้น

- Side panel แสดงครบ 3 ส่วนเสมอ: **Agenda** · **Tasks** · **Daily Note**
- ส่วนที่ว่างแสดงข้อความว่างชัดเจน **ไม่ซ่อนหัวข้อทิ้ง** — ผู้ใช้ต้องรู้ว่า "ไม่มี" ต่างจาก "ไม่มีฟีเจอร์นี้"
- ส่วน Daily Note แสดงตัวอย่าง 2–3 บรรทัดแรก + ปุ่มไป `/daily?date=YYYY-MM-DD`
- ติ๊กงานจาก panel ได้โดยตรง และผลสะท้อนกลับ `/daily` ทันที
- เปิด panel ไม่ทำให้ปฏิทินเดือนนั้นโหลดใหม่

### US-08 — เห็นภาพรวมเดือนจากหน้า Daily

- Mini Calendar แสดงเดือนปัจจุบัน ไฮไลต์วันที่กำลังดู
- วันที่มีโน้ต / มีงาน / มีนัด มีเครื่องหมายแยกชนิดได้
- คลิกวันใด ๆ เปลี่ยนวันของทั้งหน้าโดยไม่โหลดหน้าใหม่
- ใต้ Mini Calendar แสดงกำหนดการของวันแบบย่อ (เวลา + ชื่อ)

### US-09 — ลบข้อมูลได้โดยไม่ทำลายประวัติ

- ลบโน้ตรายวัน ต้องถามยืนยันและ **ระบุจำนวนงานที่ผูกอยู่**
- ลบโน้ตแล้ว งานที่ผูกอยู่ **ไม่ถูกลบตาม** แต่กลายเป็นงานที่ไม่มีโน้ตแม่
- ปฏิทินย้อนหลังยังแสดงงานที่เคยทำเสร็จในวันนั้น
- มีทางกู้คืนภายใน 30 วัน

### US-10 — ข้อมูลเก่าต้องไม่หายหลังอัปเกรด

- To-do เดิมรูป `{ text, checked }` และรูป string ล้วน ต้องย้ายเข้า `Task` ครบทุกแถว
- ตรวจนับก่อน–หลัง migration ต้องเท่ากัน และมีรายงานผล
- ระหว่างเปลี่ยนผ่าน อ่านได้ทั้งสองรูปแบบ
- rollback ได้โดยไม่สูญข้อมูล

## 4. Database Schema

### 4.1 `Note` — SSOT ของ "ข้อความ" (มีอยู่แล้ว, เพิ่มเฉพาะความสัมพันธ์)

```prisma
model Note {
  id             Int       @id @default(autoincrement())
  userId         Int?      @map("user_id")
  title          String    // "Daily Note - 16 Aug 2026" สำหรับโน้ตรายวัน
  content        String?   // ข้อความล้วนเสมอ (ใช้ค้นหา/พรีวิว)
  contentRich    Json?     // เอกสาร TipTap — จำกัด 256 KB
  type           String?   @default("text")   // 'list' = โน้ตรายวัน
  tags           Json      @default("[]")     // ['daily'] = ตัวชี้โน้ตรายวัน
  scheduledFor   DateTime? @map("scheduled_for")  // ★ กุญแจเชื่อมทุกอย่าง (เที่ยงวันท้องถิ่น)
  dueDate        DateTime? @map("due_date")
  isPinned       Boolean   @default(false)
  color          String?
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  // เก็บไว้ระหว่างช่วงเปลี่ยนผ่าน แล้วลบใน Phase 4
  checklistItems Json      @default("[]") @map("checklist_items")

  tasks          Task[]    // ใหม่
  user           User?     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, scheduledFor])
  @@map("notes")
}
```

### 4.2 `Task` — SSOT ของ "งานที่ต้องทำ" (ตารางใหม่)

```prisma
model Task {
  id           Int       @id @default(autoincrement())
  userId       Int       @map("user_id")

  text         String
  isDone       Boolean   @default(false) @map("is_done")
  completedAt  DateTime? @map("completed_at")  // ต้องเป็น null เมื่อ isDone = false

  scheduledFor DateTime  @map("scheduled_for") // ★ วันที่วางแผน (เที่ยงวันท้องถิ่น)
  dueDate      DateTime? @map("due_date")      // กำหนดส่ง แยกจากวันที่วางแผน

  position     Int       @default(0)           // ลำดับภายในวัน
  priority     String?                         // 'low' | 'normal' | 'high'

  // optional เสมอ — ลบโน้ตแล้วงานต้องไม่หายไปด้วย (D5, EC-01)
  noteId       Int?      @map("note_id")
  note         Note?     @relation(fields: [noteId], references: [id], onDelete: SetNull)

  deletedAt    DateTime? @map("deleted_at")
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt

  user         User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, scheduledFor])     // มุมมองรายวัน + ปฏิทิน
  @@index([userId, isDone, dueDate])  // Master List + งานเลยกำหนด
  @@index([noteId])
  @@map("tasks")
}
```

### 4.3 `CalendarEvent` — SSOT ของ "นัดหมาย" (ตารางใหม่)

> ⚠️ **ห้ามตั้งชื่อ `Event`** — ชื่อนั้นถูกใช้โดย error tracking ของ Bug Tracker แล้ว

```prisma
model CalendarEvent {
  id          Int       @id @default(autoincrement())
  userId      Int       @map("user_id")

  title       String
  description String?
  location    String?

  startAt     DateTime  @map("start_at")
  endAt       DateTime  @map("end_at")     // ต้อง >= startAt เสมอ (ตรวจที่ API)
  isAllDay    Boolean   @default(false) @map("is_all_day")

  color       String?
  deletedAt   DateTime? @map("deleted_at")
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  user        User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, startAt])
  @@map("calendar_events")
}
```

### 4.4 ความสัมพันธ์

| จาก | ถึง | ชนิด | เมื่อลบต้นทาง | เหตุผล |
|---|---|---|---|---|
| `User` | `Note` / `Task` / `CalendarEvent` | 1 : N | `Cascade` | ลบบัญชี = ลบข้อมูลส่วนตัวทั้งหมด |
| `Note` | `Task` | 1 : N (optional) | `SetNull` | **สำคัญที่สุด** — ลบโน้ตรายวันแล้วงานต้องอยู่ต่อ |
| `Note` | `CalendarEvent` | ไม่มี | — | เชื่อมกันด้วย "วันที่" เท่านั้น (D3) |

> **กติกาสำคัญ: ไม่มีการคัดลอกข้อมูลระหว่างตาราง**
> หน้าจอทั้งหมด (Daily, Mini Calendar, Month View, Side Panel, Master List) คือ view คนละมุมของ
> query เดียวกัน คือ "ทุกอย่างที่ `scheduledFor` อยู่ในช่วงวันที่ X–Y"
> ไม่มีงานเบื้องหลังที่คอย sync ข้ามตาราง เพราะทันทีที่มีการคัดลอก ก็จะมีวันที่ข้อมูลสองชุดไม่ตรงกัน

## 6. Edge Cases และวิธีรับมือ

ทุกข้อมาจากโค้ดจริงหรือบั๊กที่เจอแล้ว ไม่ใช่รายการสมมติ

| รหัส | สถานการณ์ | ผลถ้าไม่จัดการ | วิธีรับมือ |
|---|---|---|---|
| **EC-01** | **ลบโน้ตรายวันที่มีงานผูกอยู่** | ถ้าใช้ `Cascade` งานทั้งหมดของวันนั้นหายจากฐานข้อมูล ปฏิทินย้อนหลังกลายเป็นวันว่าง ประวัติสูญ กู้ไม่ได้ | `Task.noteId` เป็น **optional + `SetNull`** · กล่องยืนยันระบุจำนวนงานที่ผูกอยู่ · soft delete เก็บ 30 วัน |
| **EC-02** | เปิด `/daily` สองแท็บบนวันเดียวกัน แล้วทั้งคู่สร้างโน้ต | ได้โน้ตรายวันซ้ำสองใบ ปฏิทินแสดงซ้ำ งานกระจายคนละใบ | **มีทางแก้แล้ว** — `findDailyNote()` เลือกใบที่ `id` น้อยที่สุด ทุก client จึงบรรจบที่ใบเดียวกัน · ควรเสริม unique index `(userId, scheduledFor)` เฉพาะโน้ตติดแท็ก `daily` |
| **EC-03** | ผู้ใช้เดินทางข้าม timezone หรือตั้งค่าโปรไฟล์ไม่ตรงนาฬิกาเครื่อง | `/daily` คิดวันจากเบราว์เซอร์ แต่ปฏิทินคิดจาก `User.timezone` — งานบันทึกตอน 23:30 อาจไปโผล่คนละวัน | ยึด `User.timezone` เป็นแหล่งเดียว (D4) · เขียน `scheduledFor` เป็น**เที่ยงวัน**ท้องถิ่น ให้ห่างขอบวันทั้งสองด้าน 12 ชม. |
| **EC-04** | เวลาที่แสดงเพี้ยน **+7 ชม.** | โน้ตที่บันทึก 20:48 อ่านกลับมาเป็น 03:48 ของวันถัดไป | ✅ **แก้แล้ว 2026-08-17** — ดู §7 |
| **EC-05** | ติ๊กงานเสร็จ แล้วยกเลิกติ๊กภายหลัง | `completedAt` ค้างค่าเดิม รายงาน "งานที่เสร็จวันนี้" นับงานที่ยังไม่เสร็จ | บังคับที่ชั้น API: `isDone = false` ⇒ `completedAt = null` เสมอ · มี test ครอบกรณีติ๊ก–ยกเลิก–ติ๊กใหม่ |
| **EC-06** | ข้อมูล To-do รูปแบบเก่าใน `checklistItems` | ของเดิมมีทั้งรูป `{ text, checked }` และ string ล้วน — migration ที่รองรับแบบเดียวทำข้อมูลหาย | ใช้ `normalizeTodos()` ที่รองรับทั้งสองรูปเป็นตัวอ่านใน migration · เก็บ `checklistItems` ไว้อ่านอย่างเดียวหนึ่ง release ก่อนลบ · ตรวจนับก่อน–หลังต้องเท่ากัน |
| **EC-07** | โน้ตเก่าที่ `scheduledFor` เป็น null | หายจากปฏิทินทั้งหมดหลังอัปเกรด | **จัดการแล้ว** — ปฏิทิน fallback ไป `createdAt` และติดธง `isScheduled: false` · UI ต้องแยก "เขียนวันนั้น" ออกจาก "วางแผนไว้วันนั้น" |
| **EC-08** | เปิดหน้าที่มีบันทึกอยู่แล้ว แต่ระบบเปิดโหมดพิมพ์ | ผู้ใช้เห็นช่องพิมพ์แทนการ์ดทุกครั้งที่รีเฟรช | **บั๊กจริงที่แก้แล้ว** — hook เคลียร์ `loading` พร้อม `notes` แต่คัดลอกลง `richDoc` ใน effect ถัดไป การตัดสินใจจึงอ่านค่าที่ยังไม่ทันซิงก์ · **กติกา:** ตัดสินโหมดจากข้อมูลที่บันทึกแล้วเท่านั้น |
| **EC-09** | วันที่ไม่มีเนื้อหาเลย | ถ้าเขียนแถวเปล่าลง DB จะได้โน้ตว่างเปล่าเต็มปฏิทิน | คงพฤติกรรมเดิม: **วันว่างไม่เขียนแถว** · แถวถูกสร้างเมื่อมีตัวอักษรแรกหรืองานชิ้นแรกเท่านั้น |
| **EC-10** | เอกสาร rich text เกิน 256 KB | บันทึกล้มเหลวเงียบ ๆ ผู้ใช้เสียงานที่พิมพ์ | มี `RICH_TEXT_MAX_BYTES` และ `isRichDocTooLarge()` แล้ว · UI ต้องเตือน**ก่อน**ถึงเพดาน · ห้ามฝังรูป base64 (`allowBase64: false` ตั้งไว้แล้ว) |
| **EC-11** | งานค้างจากเมื่อวานที่ยังไม่เสร็จ | ถ้ายึด `scheduledFor` อย่างเดียว งานค้างจะจมอยู่ในวันเก่า | Master List ต้องมีมุมมอง "เลยกำหนด" ที่ใช้ `dueDate` · **ข้อเสนอ: ไม่ยกงานค้างมาวันปัจจุบันอัตโนมัติ** เพราะการแก้ข้อมูลเองโดยไม่ได้สั่งทำให้ประวัติของวันนั้นผิด — แสดงเป็นแถบ "ค้างจากวันก่อน" แทน |
| **EC-12** | นัดหมายคร่อมเที่ยงคืนหรือข้ามหลายวัน | โผล่แค่วันที่เริ่ม วันถัดไปดูเหมือนว่าง | query ปฏิทินใช้เงื่อนไขช่วงเวลาซ้อนทับ (`startAt < ปลายวัน AND endAt >= ต้นวัน`) ไม่ใช่จับคู่เฉพาะวันของ `startAt` |

## 7. Phase 0 — เสร็จแล้ว (2026-08-17)

เดิมเอกสารนี้กำหนดให้แก้บั๊กเวลา EC-04 ก่อนเริ่มงานอื่น เพราะ FR-3 "real-time date stamping"
วางอยู่บนค่าเวลาโดยตรง **ทำเสร็จแล้ว** และผลการวัดแก้ความเข้าใจเดิมไปสองข้อ

### สาเหตุจริง แคบกว่าที่เขียนเตือนไว้

- สมมติฐานแรกคือ DB default `CURRENT_TIMESTAMP` — **ผิด** วัดแล้วได้ 0 นาที
- ตัวที่เพี้ยนคือ **`@updatedAt` ของ Prisma เอง เฉพาะตอน UPDATE** พอดี 420 นาที
- กลไก: Prisma ส่งค่ามาถูก (`06:02:22.544 UTC`) แต่คอลัมน์เป็น `timestamp without time zone`
  Postgres จึงอ่าน suffix `UTC` เป็น timestamptz แล้วแปลงเข้า session timezone (Asia/Bangkok)
  ก่อนเก็บ พอส่งกลับมาไม่มี zone ติด Prisma เลยติดป้าย `Z` ให้
- **`scheduledFor` และ `dueDate` ถูกต้องทั้ง insert และ update** — วันในปฏิทินไม่เคยเพี้ยน
  ข้อนี้สำคัญ เพราะเอกสารฉบับแรกเตือนเกินจริง

### สิ่งที่ทำ

| ไฟล์ | หน้าที่ |
|---|---|
| `app/server/src/lib/prisma.ts` | ตรึง session timezone เป็น UTC **ในโค้ด ไม่ใช่ `DATABASE_URL`** เพราะถ้าอยู่ใน env แล้วใครลืมใส่ ผลคือข้อมูลเพี้ยนเงียบ ๆ ไม่ใช่ server ไม่ขึ้น |
| `app/server/src/scripts/repair-updated-at-skew.ts` | ซ่อมข้อมูลเก่า 40 แถวใน 6 ตาราง |
| `app/server/src/scripts/rename-daily-notes.ts` | เปลี่ยนชื่อโน้ตเก่า 4 ใบเป็นรูปแบบตามสเปก |

### บทเรียนจากสคริปต์ซ่อมข้อมูล — อ่านก่อนเขียนสคริปต์แนวนี้อีก

1. **กฎตรวจจับแรกหลวมเกินไป** ใช้ `updated_at ≠ created_at` แล้ว safety check พบว่า
   **6 แถวจะถูกดันไปก่อน `created_at` ตัวเอง** ซึ่งเป็นไปไม่ได้สำหรับค่าที่เพี้ยนจริง =
   พิสูจน์ว่า 6 แถวนั้นไม่เคยเพี้ยน กฎหลวมจะไปทำพังในทางกลับกัน
   เปลี่ยนเป็น `updated_at >= created_at + offset`
2. **สคริปต์นี้รันซ้ำแล้วข้อมูลพัง** แถวที่ถูกแก้ห่างจากตอนสร้างเกิน 7 ชม. จริง ๆ ยังเข้าเงื่อนไข
   หลังซ่อม รันอีกรอบจะลบอีก 7 ชม. จึงมี ledger `_timestamp_repairs` กันไว้ และปฏิเสธการเขียนรอบสอง
   เว้นแต่ส่ง `--force` — **ห้ามถอดตัวกันนี้ออก**
3. สคริปต์เปลี่ยนชื่อโน้ตรันซ้ำได้ปลอดภัย เพราะแปลงจากรูปเก่าเป็นรูปใหม่ **ไม่ใช่คำนวณจากค่าปัจจุบัน**

### เฟส 3.5 — ถอด `/daily`, รวมเข้าเป็นสองหน้า (เสร็จ 2026-08-19)

การมีทั้ง `/daily` (เขียนโน้ตรายวัน + todo แบบ inline) และ `/notes` (การ์ดโน้ตทุกใบ) พร้อมกัน
สร้างคำถามซ้ำ: โน้ตของวันนี้ต้องเปิดที่ไหน สีของโน้ตตั้งได้จากที่ไหน งานเพิ่มได้จากกี่จุด
— เฟสนี้ยุบให้เหลือหน้าที่ชัดเจนของแต่ละหน้าเดียว:

- **`RichTextEditor` (ตัวเดียวกับที่ `/daily` เคยใช้) ย้ายเข้า `/notes`** ผ่าน component ใหม่
  [`NoteForm.tsx`](../../../app/client/src/components/notes/NoteForm.tsx) — ใช้ทั้งตอนสร้างโน้ตใหม่
  และตอนแก้ไข (`EditNoteDialog`) เดิม `EditNoteDialog` เป็น `<textarea>` ธรรมดา บันทึกทับ
  `contentRich` ทุกครั้งที่แก้ — ตอนนี้แก้ในตัวเอดิเตอร์เดิม ไม่ทิ้ง formatting อีกแล้ว
- **สีโน้ตตั้งได้จากฟอร์มโดยตรง** — [`NoteColorPicker.tsx`](../../../app/client/src/components/notes/NoteColorPicker.tsx)
  เดิมตั้งได้จากเมนูคลิกขวาบนการ์ดเท่านั้น (แปลว่าต้องมีโน้ตอยู่ก่อน) พาเลตต์ย้ายไปเป็น
  [`lib/noteColors.ts`](../../../app/client/src/lib/noteColors.ts) ที่เดียว ใช้ร่วมกันทั้งฟอร์ม
  เมนูคลิกขวา และชิปบนปฏิทิน
- **`/tasks` เพิ่มปุ่มสร้างงานได้** — [`TaskComposer.tsx`](../../../app/client/src/components/tasks/TaskComposer.tsx)
  ก่อนหน้านี้เพิ่มงานได้เฉพาะจาก `/daily` เท่านั้น ทำให้หน้าที่แสดง "ทุกงานที่ต้องทำข้ามทุกวัน" (US-06)
  เพิ่มงานเองไม่ได้ ตอนนี้ CRUD ครบทั้งสี่ตัวบนหน้าเดียว
- **Day panel เปิดฟอร์มเขียนโน้ตแทนการนำทางออกจากปฏิทิน** — ปุ่ม "Write this day" ใน
  `DayDetailPanel` เดิมลิงก์ไป `/daily?date=`, ตอนนี้เรียก `onWriteNote` ที่เปิด `NoteForm`
  ในหน้า `/notes` เอง ผู้อ่านไม่หลุดออกจากปฏิทินที่กำลังดูอยู่
- **`/tasks` ลิงก์ไปวันบนปฏิทินผ่าน `?day=`** แทน `/daily?date=` — `NotesCalendar.tsx` อ่านพารามิเตอร์นี้
  ครั้งเดียวแล้วลบออกจาก URL เหมือนที่ `?note=` ทำอยู่แล้ว

**สิ่งที่หายไปพร้อม `/daily` และยังไม่มีที่แทน:** แถบ "Still open from earlier" (mitigation ของ EC-11
เดิม ดู §8 หัวข้อถัดไป) ไม่มีที่อยู่แล้วเพราะเคยอยู่บนหน้า `/daily` โดยเฉพาะ ตัวแทนตอนนี้คือฟิลเตอร์
**Overdue** บน `/tasks` (query ข้ามทุกวัน ไม่ใช่แค่ "ก่อนวันที่เปิดอยู่" แบบเดิม) หลักการที่เคาะไว้ —
**ไม่ยกงานอัตโนมัติ** — ยังคงอยู่ครบ แต่รูปแบบการนำเสนอเปลี่ยนจากแถบเฉพาะที่เป็นฟิลเตอร์ทั่วไป
ถ้าต้องการแถบเฉพาะกลับมาบน `/tasks` ยังไม่ได้ทำ

**ไฟล์ที่ถูกลบ:** `pages/DailyNote.tsx`, `hooks/useDailyTodos.ts`, `hooks/useCarriedOverTasks.ts`,

## 9. นอกขอบเขตเวอร์ชันนี้

- **การรวมกับ Bug Tracker** — `Issue` และ `Ticket` เป็นงานของทีม ไม่ใช่งานส่วนตัว ไม่ควรปนกันในมุมมองเดียว
